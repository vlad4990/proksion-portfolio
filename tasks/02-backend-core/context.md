# Context — 02 backend-core

## Цель в одной строке
Слой данных и каркас бэкенда: `bun:sqlite`, схема + раннер миграций, типизированные
репозитории, slug-утилита, конфиг — всё под TDD (`bun test`). HTTP-эндпоинтов пока минимум.

## Опорные разделы спеки
- §3 (схема SQLite, PRAGMA, правила слагов), §7 (зависимости: без ORM, сырой `bun:sqlite` +
  тонкий слой репозиториев), §11 (env `DATABASE_PATH`, структура `/back`).

## Что уже есть (после задачи 01)
- `back/` — stub Elysia с `GET /health`, `oven/bun:1`-образ, слушает `BACK_PORT`.
- `app_data` volume под SQLite (`DATABASE_PATH=/data/db.sqlite`).

## Методология — TDD (обязательно)
- `bun test` (встроен, без зависимостей). Сначала падающий тест → реализация → рефактор.
- Тесты гоняют против временной/in-memory БД (`:memory:` или temp-файл), не против `/data`.
- Тесты коммитятся вместе с кодом; каждый репозиторий и slug-утилита покрыты.

## Ключевые требования из §3
- `PRAGMA journal_mode=WAL; PRAGMA foreign_keys=ON;`.
- Таблицы: `category`, `subcategory`, `work`, `image` (см. DDL в §3). FK с `ON DELETE CASCADE`
  (а `work.cover_image_id` — `ON DELETE SET NULL`). Уникальность слагов в своей области:
  `category.slug` глобально; `subcategory(category_id, slug)`; `work(subcategory_id, slug)`.
- Слаги: транслит ru→lat → lowercase → пробелы в `-` → только `[a-z0-9-]` → уникальность
  суффиксом `-2/-3`. Пустой title → fallback (напр. на короткий id). Слаг стабилен после
  создания.

## Инварианты / ограничения
- Без ORM и без миграционных фреймворков — миграции это `.sql`-файлы + свой раннер,
  отслеживающий применённые (таблица `_migrations` или `PRAGMA user_version`), идемпотентный.
- Никаких `any`, strict TS. Репозитории возвращают типизированные строки.
- Публичные/админ-эндпоинты — НЕ здесь (это задачи 03/05/06). Здесь — слой данных + утилиты.
