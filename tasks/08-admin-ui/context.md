# Context — 08 admin-ui

## Цель в одной строке
Экраны управления контентом в админке: CRUD категорий/подкатегорий/работ, загрузка картинок,
drag-n-drop сортировка, редактор описаний — на shadcn/ui, с TDD для логики.

## Опорные разделы спеки
- §3 (модель), §7 (admin-эндпоинты), §8 (админка — отдельный проект).

## Что уже есть
- Каркас админки: Tailwind+shadcn, роутер, API-клиент, auth-флоу, Vitest+RTL (задача 07).
- Серверный admin-API: CRUD + upload + reorder (задача 06), публичные контракты (03).

## Методология
- **TDD** для логики: маппинг данных ↔ форм, валидация, состояние загрузки картинок
  (state machine), вычисление payload для reorder. Vitest + RTL.
- UI-разметка — компонентно (без тест-ферст), поведение покрываем RTL где есть логика.

## Экраны (минимум)
- Список **категорий** → CRUD; внутри — **подкатегории** → CRUD.
- **Работы** подкатегории: создать/редактировать (title, **описание**, выбор cover, порядок),
  удалить. Внутри работы — **картинки**: мультизагрузка с прогрессом, alt, удаление, выбор cover.
- **Сортировка** (drag-n-drop) для категорий/подкатегорий/работ/картинок → `reorder` API.

## Инварианты / ограничения
- Strict TS, без `any`. Один layout (десктоп). Все запросы — через API-клиент (07) с CSRF.
- Описание: формат plain/markdown — согласовать с решением бэка (§7/§13); если markdown — лёгкий
  ввод (textarea + превью), без тяжёлых редакторов.
- Drag-n-drop — лёгкая зависимость (напр. `@dnd-kit`) допустима (изолировано в `/admin`).
- Опираться на стабильные контракты задач 03/06; не менять серверный API в рамках этой задачи.

## На что НЕ замахиваться
Изменения серверного API, бэкап, публичный фронт.
