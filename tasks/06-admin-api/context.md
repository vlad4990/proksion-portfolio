# Context — 06 admin-api

## Цель в одной строке
Защищённые admin-CRUD эндпоинты (категории/подкатегории/работы/картинки/сортировка) поверх
auth (05) и storage (04), с авто-слагами и загрузкой картинок через пайплайн sharp.

## Опорные разделы спеки
- §7 (таблица admin-эндпоинтов), §3 (модель, cover-логика), §5/§6 (хранилище/обработка),
  §9 (хук «данные изменились» для бэкапа).

## Что уже есть
- Репозитории + slug (02), публичные контракты (03), storage+pipeline+store (04),
  auth guard + CSRF (05).

## Методология — TDD
- Тесты first: каждый эндпоинт доступен только с валидной сессией; create генерирует слаг из
  title (с уникальностью); upload создаёт строку `image` + варианты в MinIO; delete каскадит и
  чистит объекты S3; reorder сохраняет `sort_order`; cover-логика.
- Загрузка/удаление — интеграционно против `minio`.

## Эндпоинты (роуты от корня; снаружи `/api/admin/...`)
- `POST/PATCH/DELETE /admin/categories[/:id]`
- `POST/PATCH/DELETE /admin/subcategories[/:id]`
- `POST/PATCH/DELETE /admin/works[/:id]` (title/description/cover/order)
- `POST /admin/works/:id/images` (multipart → `images/store` → строка `image`)
- `PATCH/DELETE /admin/images/:id` (alt/порядок/удаление; удаление чистит объекты S3)
- `PATCH /admin/.../reorder` (sort_order для категорий/подкат/работ/картинок)

## Инварианты / ограничения
- Все мутации — за guard'ом (05) и под CSRF. Strict TS, без `any`.
- Слаг генерируется из title (slug-утилита 02), редактируем, уникален в своей области,
  стабилен после создания (смена title не пересоздаёт слаг).
- Cover: при первой загруженной картинке работы — выставить `cover_image_id`; при удалении
  cover — переназначить (или NULL). Циклическая ссылка (02) уже поддержана.
- **Хук бэкапа:** на каждой успешной мутации вызывать `onMutation()` (пока — лёгкий стабильный
  хук/событие; реальную rclone-логику подключит задача 11). Не реализовывать сам бэкап здесь.

## На что НЕ замахиваться
UI админки (07–08), rclone/бэкап-транспорт (11). Только серверные эндпоинты.
