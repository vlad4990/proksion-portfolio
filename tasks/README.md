# Tasks — функциональная часть PROKSION (бэкенд, админка, инфра)

Нарезка работ по превращению портфолио из статических заглушек в управляемое приложение
(бэкенд + хранилище + админка + бэкап). **Единый источник правды по архитектуре —
[`docs/architecture.md`](../docs/architecture.md)**; задачи ссылаются на её разделы (§N).

> История ранней миграции на Astro — в [`_legacy-astro/`](./_legacy-astro/) (стек с тех пор
> сменился на Vite+React SPA; читать только как исторический контекст).

---

## Как заводить задачу

Каждая задача — **отдельная папка** `NN-kebab-case` (номер + 2–3 слова через дефис).
Внутри — ровно три файла:

```
tasks/
├── README.md                  ← этот файл (конвенция + индекс)
└── NN-task-name/
    ├── context.md             ← необходимый контекст: ссылки на §спеки, что уже есть в репо,
    │                            инварианты/ограничения, на что НЕ замахиваться
    ├── task.md                ← тело задачи = промпт агенту: цель, пошаговые инструкции,
    │                            deliverables, методология (TDD/SDD)
    └── verify.md              ← как проверить корректность: чек-лист + команды + критерии Done
```

**Принципы:**

- **Самодостаточность.** Агент выполняет задачу, читая свою папку + `docs/architecture.md`.
  Если для работы нужен артефакт другой задачи — это явная зависимость (см. индекс ниже).
- **Definition of Done** = все пункты `verify.md` пройдены.
- **Один слой — одна папка.** Бэкенд/админка/фронт не смешиваются в одной задаче.
- **Не расширять скоуп.** Что вне задачи — оставить заглушкой/TODO и отметить в отчёте.

### Рабочая процедура

```
1. Открыть tasks/NN-name/ — прочитать context.md, затем task.md.
2. Выполнить task.md (соблюдая методологию задачи: TDD или SDD).
3. Пройти tasks/NN-name/verify.md по пунктам, починить недочёты.
4. Закоммитить и перейти к следующей задаче (с учётом зависимостей).
```

## Методология (по слоям)

| Слой | Подход | Что это значит | Инструменты |
|---|---|---|---|
| **`/back`** (вся логика) | **TDD** | Сначала падающий тест → реализация до зелёного → рефактор. Тесты коммитятся вместе с кодом. | `bun test` (встроен в Bun, без зависимостей) |
| **`/admin`** (логика: api-клиент, сторы, хуки, валидация форм) | **TDD** | То же тест-ферст для НЕ-визуальной логики. | Vitest + `@testing-library/react` |
| **`/admin`** (UI-компоненты) | компонентный | Радикального тест-ферст для разметки не требуем; покрываем поведение (interaction) там, где есть логика. | shadcn/ui + Tailwind; RTL для поведения |
| **`/front`** (публичное портфолио) | **SDD** | Spec-Driven: реализация строго по `docs/architecture.md` + `task.md`. Без тест-ферст. | проверка = `npm run build` (tsc strict) + визуальный чек-лист |

> Тест-тулинг (`bun test`, Vitest) вводится **только** в `/back` и `/admin` — это новое для
> проекта. `/front` сохраняет действующую конвенцию «проверка = build + визуал» (см.
> `front/CLAUDE.md`). Линтера/форматтера в проекте по-прежнему нет.

## Незыблемые рамки (применяются ко всем задачам)

Из корневого `CLAUDE.md` и `front/CLAUDE.md`:

1. **Бренд — святое.** Цвета/шрифты/размеры публичного фронта — только токены
   `front/src/styles/tokens.css`. Никаких новых hex/эмодзи/градиентов/glass. (Админка —
   back-office, строгих рамок бренда нет; токены можно переиспользовать опционально.)
2. **TypeScript strict** везде, никаких `any`.
3. **UI-тексты — русские.** Display-заголовки публичного фронта — uppercase.
4. **Минимум зависимостей** в публичном `/front`. Тяжёлые UI-либы допустимы только в
   изолированном `/admin` (свой бандл, не влияет на вес сайта).
5. **Двойное дерево** desktop/mobile — только для публичного фронта; фичи делаются в обоих.
