# Context — 13 db-tags-featured

## Зачем

Редизайн листинга проектов (спека: [`docs/projects-redesign.md`](../../docs/projects-redesign.md),
далее «спека», §4) требует новых данных: глобальные теги-фильтры, кураторская витрина
разделов, контентные поля категории (оверлайн, роль, период, длинное описание, вариант
секции). Это чисто **слой данных**: миграция + типы строк + репозитории + сид. Публичный
и админский API — задачи 14 и 15.

## Что уже есть в репо

- **Механизм миграций** — `back/src/db/migrate.ts`: `.sql`-файлы из `back/migrations/`
  сортируются лексикографически, каждая непримененная накатывается в своей транзакции,
  имя пишется в `_migrations`. Новая миграция = положить файл `0002_<name>.sql` — накатится
  на старте бэкенда и в каждом тесте (`openDb(':memory:')` в `back/src/db/index.ts:14-20`
  прогоняет `migrate()`).
- **Единственная миграция** — `back/migrations/0001_init.sql`: `category`, `subcategory`,
  `work`, `image` + индексы по FK. Даты — TEXT `datetime('now')`.
- **Типы строк** — `back/src/types.ts` (strict-интерфейсы; репозитории делают `SELECT *`,
  но типы описывают колонки явно — правятся синхронно с миграцией).
- **Репозитории** — `back/src/db/repositories/{category,subcategory,work,image}.ts`:
  тонкие CRUD поверх `bun:sqlite`, частичный UPDATE через `runUpdate`
  (`_helpers.ts:13-38` — динамический SET по allowlist полей + `RETURNING *`).
- **Сид** — `back/src/seed.ts` (`seed(db)`, идемпотентный): 3 категории / 5 подкатегорий /
  7 работ / 11 картинок; используется тестами (`routes/public.test.ts:22`) как фикстура.
- **Прод-дамп для проверки** — `prod-dump/db.sqlite` (копию можно мигрировать локально,
  сам файл не трогать).

## Инварианты / ограничения

- Стек зафиксирован: `bun:sqlite`, **без ORM**; сырые SQL в репозиториях.
- SQLite `ALTER TABLE` ограничен: только `ADD COLUMN` (нам большего и не надо);
  `NOT NULL` — обязательно с `DEFAULT`; `CHECK` в `ADD COLUMN` допустим.
- Down-миграций нет — миграция должна быть корректной с первого раза.
- `PRAGMA foreign_keys=ON` уже включён — FK в новых таблицах работают.
- Методология — **TDD** (`bun test`): сначала падающий тест, потом код.
- Инвариант витрины: `featured_order` уникален в пределах **категории** (категория
  работы определяется через её подкатегорию). Обеспечивается кодом — атомарной
  перезаписью списка (см. API в спеке §5.5), не констрейнтом.
