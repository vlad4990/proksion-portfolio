# Task — 09 front-listing

**Слой:** `/front`. **Методология:** **SDD** (по спеке; проверка = build + визуал, без тестов).
Спека: §8, §7, §4 + `front/CLAUDE.md`.

## Цель
Листинг проектов (и `/projects`, и `/projects/:cat/:sub`) рендерится из API — в обоих деревьях,
с сохранением masonry-раскладки, skeleton-состояний и резервирования `aspect-ratio`.

## Шаги

1. **API-клиент фронта** — `src/api/` (тонкие `fetch`-обёртки + типы ответов под контракты 03).
   База — `/api`. Типы тайла `{id,src,w,h}` и навигации (категории/подкатегории).
2. **Vite dev-proxy** — `vite.config.ts`: `/api`→`http://localhost:3001`, `/media`→MinIO (или
   через back). Dev-сервер остаётся на 5005 (Chrome MCP).
3. **Десктоп** (`ProjectsScreen.tsx`) — заменить хардкод `GROUPS`/тайлов на загрузку из API
   (по маршруту: все работы для `/projects`, либо работы подкатегории для `/projects/:cat/:sub`).
   Навигация по категориям/подкатегориям — из API. Skeleton на время загрузки (тон `--c-skeleton`),
   состояние «пусто»/ошибка.
4. **Мобайл** (`MobileProjects.tsx`) — то же самое во втором дереве (данные больше не дублируются
   хардкодом — единый источник API).
5. **Тайлы** — сохранить `<Masonry>`-контракт и форму `{id,src,w,h}`: `aspect-ratio` из `w/h`
   (без скачков layout), `loading="lazy"`, `decoding="async"`. Клик пока может быть инертным
   (модалка — задача 10), но `id` сохраняем как ключ/задел.

## Требования
- Strict TS, без `any`. Никаких новых зависимостей в `/front`. Токены/бренд не нарушать.
- Оба дерева функционально эквивалентны (с поправкой на разную разметку desktop/mobile).
- Грейсфул-обработка пустого ответа и ошибки сети (не белый экран).

## Deliverables
`front/src/api/*`, dev-proxy, листинг из API в `ProjectsScreen.tsx` + `MobileProjects.tsx`
со skeleton/empty/error. `npm run build` зелёный; визуальный чек-лист пройден.
